# NiniMed Plesk Deployment

This repository is prepared for deployment to Plesk with GitHub Actions. It uses Next.js `output: "standalone"`, so the deployment package contains the production server generated by Next.js and does not require a custom `server.js` in the repository or a full dependency reinstall on the server.

## 1. Plesk setup

Create a subdomain such as `app.example.com` and enable the Plesk Node.js extension.

Configure the Node.js application:

- Node.js version: 20.x
- Application mode: `production`
- Application root: `/var/www/vhosts/example.com/app.example.com/current`
- Application startup file: `server.js`
- Document root: the subdomain document root created by Plesk
- Passenger app environment: production

The generated standalone `server.js` listens on the `PORT` supplied by Plesk. Do not hard-code a public port or add an Apache/nginx reverse proxy when using the Plesk Node.js extension; Plesk supplies the proxy layer.

The workflow deploys releases to:

```text
/var/www/vhosts/example.com/app.example.com/releases/<commit-sha>
/var/www/vhosts/example.com/app.example.com/current -> releases/<commit-sha>
```

Before the first deployment, update `DEPLOY_PATH` in `.github/workflows/deploy-plesk.yml` to match the actual system-user path. The SSH user must own or be able to write to that directory.

## 2. Production environment variables

Set these in Plesk under the Node.js application's environment variables. Do not commit `.env`, `.env.production`, API keys, database passwords, or private keys.

Required for the application:

```text
NODE_ENV=production
PORT=<provided by Plesk, do not hard-code unless Plesk requires it>
DATABASE_URL=postgres://<user>:<password>@<host>:5432/<database>
REDIS_URL=redis://<host>:6379
NEXT_PUBLIC_APP_URL=https://app.example.com
NEXT_PUBLIC_APP_NAME=NiniMed Enterprise CDSS
NEXT_PUBLIC_APP_VERSION=3.0.0-enterprise
```

Optional integrations used by this repository:

```text
GEMINI_API_KEY
GEMINI_API_KEY_1
GEMINI_API_KEY_2
GEMINI_API_KEY_3
OPENAI_API_KEY
GOOGLE_AI_API_KEY
ANTHROPIC_API_KEY
TELEGRAM_BOT_TOKEN
NEXT_PUBLIC_TELEGRAM_BOT_USERNAME
ENCRYPTION_MASTER_KEY
AUDIT_HMAC_SECRET
```

Use strong, unique production values for `ENCRYPTION_MASTER_KEY` and `AUDIT_HMAC_SECRET`. The database must be reachable from the Plesk host, and the database schema/migrations must be applied before users access the application.

## 3. GitHub Actions secrets

Add these repository secrets under **Settings > Secrets and variables > Actions**:

```text
PLESK_HOST
PLESK_USERNAME
PLESK_SSH_PRIVATE_KEY
PLESK_DEPLOY_PATH
PLESK_DOMAIN
NEXT_PUBLIC_APP_URL
NEXT_PUBLIC_API_URL
```

`PLESK_SSH_PRIVATE_KEY` is the private key for the Plesk system user. Never place it in the repository or in a workflow file.

The workflow also accepts the legacy secret name `SSH_PRIVATE_KEY` as a fallback. Prefer `PLESK_SSH_PRIVATE_KEY` for new setup. The key must include the complete OpenSSH private-key block, including its `BEGIN` and `END` lines.

The workflow is triggered by pushes to `main` and can also be started manually with **Run workflow**.

## 4. First deployment

1. Add `PLESK_DEPLOY_PATH` with the real path, for example `/var/www/vhosts/example.com/app.example.com`.
2. Configure the Plesk Node.js application and environment variables.
3. Confirm the SSH user can write to the deployment path.
4. Push to `main` or run the workflow manually.
5. In Plesk, confirm the application root points to `current` and the startup file is `server.js`.
6. Open `https://app.example.com/api/v1/system/health` and the application home page.

The workflow builds on GitHub, packages `.next/standalone`, `.next/static`, and `public`, uploads the package, creates a release, switches the `current` symlink, and asks Plesk to restart the application.

## 5. Rollback

The workflow removes old releases after switching to the new release. For a rollback, deploy the desired commit again from GitHub using **Run workflow**. This recreates a clean release from that commit and switches `current` back to it.

If the Plesk CLI is unavailable to the SSH user, the workflow still completes the file release but prints a restart warning. Restart the Node.js application from **Plesk > Domains > app.example.com > Node.js**.

## 6. Realtime notifications and infrastructure

The application uses server-side SSE for notifications. A single Plesk Node.js process supports the in-memory event bus for connected clients. For multiple application instances or multiple servers, configure a shared Redis pub/sub adapter before scaling horizontally; otherwise an event emitted on one process will not reach clients connected to another process.

PostgreSQL and Redis are not created by this workflow. Use managed services or provision them separately, then set `DATABASE_URL` and `REDIS_URL` in Plesk.

## 7. Troubleshooting

- **502 Bad Gateway:** verify Node.js support is enabled, the application root is `current`, and `server.js` exists at `current/server.js`.
- **Database connection errors:** verify `DATABASE_URL`, firewall rules, TLS requirements, and that the database is reachable from the Plesk host.
- **Assets return 404:** verify `.next/static` and `public` exist under `current`.
- **Notifications do not update live:** verify the browser can keep an SSE connection to `/api/v1/notifications/stream` and avoid proxy buffering for that endpoint.
- **Workflow does not restart:** restart the Node.js application manually in Plesk and verify the system user can execute the Plesk CLI.
- **Build-time environment errors:** add required `NEXT_PUBLIC_*` values as GitHub Actions secrets. Server-only secrets belong only in Plesk.
